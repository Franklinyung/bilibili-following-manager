# AI 分组写入失败问题汇总（疑似 B 站风控 block）

> 最后更新：2026-08-28
> 影响范围：AI 分组的「应用写入」阶段
> 相关版本：v0.10.4 → v0.10.5（含未提交修复）
> 一句话结论：AI 分析阶段正常（走 LLM），失败集中在把建议写回 B 站分组接口时触发风控（-352 / -412），当前脚本缺少熔断与写入断点，连续失败会进一步放大风控。
>

>
> 全部按第 9 节调研结论落地，PR 仍未发布（仅本地工作区）。

> |---|---|---|
> | **P0-1 风控熔断** | `request()` 收到 -352/-412 立即抛出不重试；新增 `onRiskAbort` 回调让外层感知熔断并 `break` | `bilibili-following-manager.user.js` `request()` |

>
> **风险点**：
> 1. 块 10 + 随机 1.5-3s 的延迟会显著拖慢：100 mid × 单组 → ~15-30s；300 mid × 多组 → 5-15 min，需向用户预告。
> 2. 本地缓存去重依赖 `storage.state.following` 同步时的 tagids 完整度；如果用户从未同步过，去重不会生效（fallback 走全集）。
> 3. -352 后强制 break 的设计会丢剩余分组写入；如果用户希望「能写多少写多少」，需要 P1 增加「局部继续」开关。

## 1. 用户可见现象

- AI 分析正常完成，建议弹窗能正常展示
- 点击「应用勾选项」后，写入阶段大量失败：
  - 报 `API -352: ...`（风控拦截）
  - 或 `API -412: ...`（请求过快）
  - 或最终报告「加入分组失败 N 个」
- 部分场景疑似「静默 block」：接口看起来成功，但刷新 B 站网页后分组没变化
- 批量越大越容易失败；分多次小批量手动应用成功率更高
- 同一账号短时间内反复重试后，后续更容易全部失败

## 2. 涉及的写接口与调用链

```text
ui._applyAISuggestions(suggestions)
  ├─ api.createGroup(name)            # 每个新分组 1 次写（/x/relation/tag/add）
  ├─ api.listGroups()                 # 创建后刷新（读）
  └─ api.addUsersToGroup(tagid, mids) # /x/relation/tags/addUsers
       └─ 每 25 个 mid 一块
            ├─ utils.windGuard()      # 按风控等级自适应 sleep
            ├─ POST tags/addUsers
            ├─ utils.windRecord()     # 埋点到风控日历
            └─ 块间 _sleep(600ms)
  └─ 组与组之间 _sleep(300ms)
```

`api.removeUsersFromGroup()`（批量移出）和 `api.unfollow()`（取关）走同一套风控护栏。

## 3. 错误码含义与脚本行为

| code | 含义 | 脚本当前行为 |
|---|---|---|
| 0 | 成功 | 正常返回 |
| -101 | 未登录 / 登录态失效 | 抛 `NOT_LOGGED_IN`，不重试 |
| -352 | 风控拦截（行为被判定异常） | 请求层退避 5s→10s→20s（仅 GET）；写入失败进入 `failedAdds` |
| -412 | 请求过快 | 同上 |

注：v0.10.5 起 POST（不可逆写操作）默认不再自动重试，避免超时后重复写；指数退避重试主要作用于 GET 读接口。

## 4. 根因假设（按可能性排序）

### 4.1 短时间写请求过多（最可能）★

一次「应用」可能触发几十上百次写请求：

- N 个新分组 → N 次 `createGroup`
- 每组 `addUsersToGroup` 至少 1 次（超过 25 人再拆块）
- 组间仅 300ms + windGuard，块间仅 600ms + windGuard

B 站按「账号 + IP + 频率 + 行为」综合判定，超过阈值即返回 -352。

### 4.2 fids 参数过长

25 个 mid 用逗号拼接成 `fids`，请求体很长，属于容易命中风控的特征。

### 4.3 createGroup 与首次 addUsers 紧邻

新建分组后立刻写第一块用户，两次写之间没有强制间隔。

### 4.4 失败后继续写（无熔断）

`_applyAISuggestions` 中某一组 `addUsersToGroup` 失败只记录到 `failedAdds`，然后继续写下一组。实际表现往往是：一个 -352 后面跟着一串失败，进一步推高风控等级。

### 4.5 重复写入放大

- 断点续传只覆盖「AI 分析阶段」，不覆盖「应用写入阶段」
- 写入失败后用户只能整轮重来，已经成功的组会被再次写入
- 恢复的历史建议与新建议可能混合，再次应用时产生重复写

### 4.6 B 站接口策略变化（待取证）

不排除 `tags/addUsers` 增加了额外校验（签名 / 来源 / 频率），需要抓包对比网页端正常操作的请求差异。

### 4.7 「返回 0 但未生效」的静默 block（待确认）

目前代码不做写后验证，`code === 0` 就当成功，无法区分「真成功」与「假成功」。

## 6. 当前缺口（v0.10.6 已堵 P0，剩余 P1/P2 见第 8 节）

> **v0.10.6 已修**：以下 4 项为 P0 缺口，本版本全部修复，详见第 0 节。其余 P1/P2 仍是真实问题。

- [ ] **无熔断**：某组 -352 后继续写后续组，连锁触发
- [ ] **无写入断点**：中断/失败后只能整轮重来，会重复写已成功部分
- [ ] **间隔偏激进且是固定值**：组间 300ms、块间 600ms，既低于社区安全线，固定节奏也容易被识别为机器行为（同类项目全部使用随机间隔）
- [ ] **无「仅重试失败项」入口**：用户只能全量重跑
- [ ] **无写后验证**：code 0 不代表真的生效，疑似静默 block 无法识别
- [ ] **windGuard red=5min/块**：大批量可能耗时数小时，且不保证成功
- [ ] **createGroup 失败后仍尝试匹配并 addUsers**，浪费写请求

## 8. 建议修复方向

### P0（先止损）

1. **熔断**：apply 过程收到一次 -352 → 立即终止本轮后续写入，提示「已触发风控，请 X 分钟后再试」
2. **写入断点**：按组记录 done / failed / pending，中断后只重试失败与未处理组，不重复写已成功组
3. **随机化降频**（参考区间见第 9 节调研）：写块 25→10；块间改为随机 2–8s；组间随机 3–10s；触发过 -352 后切换保守档（随机 5–20s）。不要用固定间隔，固定节奏本身就是可识别特征
4. **单轮总量上限**：单次「应用」限制写请求数（如 ≤100 个），超出提示分轮处理，避免账号级风控
5. **UI 增加「仅重试失败项」**，替代整轮重跑

### P1（可靠性）

6. **写后验证**：addUsers 返回 0 后，读回分组校验成员是否真的变化，识别「假成功」
7. **createGroup 与首次 addUsers 强制间隔 ≥2s**
8. createGroup 失败的组直接标记跳过，不再尝试 addUsers
9. windGuard red 时显示预计剩余时间，并允许用户主动取消

### P2（长期）

10. 抓包对比网页端请求，确认是否需要补 header / 签名 / 换新端点
11. 把风控日历状态（windStatus）导出，帮助用户判断「当前是否适合写入」

## 9. 网上同类项目方案调研（2026-08）

调研了处理 B 站批量写操作风控的开源项目、用户脚本反馈与社区 API 文档，结论如下。

### 9.1 方案对照

| 来源 | 核心做法 | 对本项目的启示 |
|---|---|---|
| [wuko233/bili-follow-cleaner](https://github.com/wuko233/bili-follow-cleaner) | 每次取关后**随机延迟 5–20s**；官方说明"遇 -352 暂停脚本、等待后增大延迟参数" | 我们的 600ms/300ms 固定间隔明显低于社区安全线；写入默认档应随机秒级，遇险后切保守档 |
| [YZz-S/Bilibili-batch-operation-tool](https://github.com/YZz-S/Bilibili-batch-operation-tool) | 标准模式随机 3–5s / 保守模式随机 5–8s；**连续失败 5–10 次自动暂停 10–20s**；断点续传**跳过已处理用户** | 引入标准/保守两档；加连续失败计数与冷却；写入阶段必须有断点且跳过已成功项 |
| Greasy Fork「bilibili 批量自动拉黑/取关工具」 | 即便是单用户级写操作，也保持**每 1.5–3s 一个** | 单请求改 25 人比逐个写更激进；块上限应 ≤10，且块间随机秒级 |
| [MrXJG/bilibili-auto-unfollow-all 实战记录](https://www.xiangjigong.top/article/bilibili-auto-unfollow-all-tampermonkey/) | 实测直接 API 循环必然撞 -352；**-352 是停止信号而非重试信号**；改走**网页原生控件**逐个操作（每页 24 个、单次 600–900ms 随机、点击后校验按钮状态变化、localStorage 跨刷新续跑）；手机号验证一律暂停交还用户，绝不绕过 | 熔断是第一优先级；中期可做「原生控件兜底路线」；每次写后读回验证（fail-closed）；验证弹窗交给用户 |
| [bilibili-API-collect：v_voucher 机制](https://github.com/pskdje/bilibili-API-collect/blob/main/docs/misc/sign/v_voucher.md) | -352 响应可能携带 `data.v_voucher` / 响应头 `x-bili-gaia-vvoucher`；流程：`/x/gaia-vgate/v1/register` → 用户完成极验 → `/validate` 换 `grisk_id` → 原请求带 `gaia_vtoken` 恢复 | 高级兜底：识别 v_voucher，弹出验证 UI 交用户完成后恢复。文档明确「不是所有风控都能走 captcha 解除」，只作 P2 |
| bujic.cc / RSSHub issue 等社区文章 | -352 常见诱因：缺 `buvid3`/`buvid4`/`bili_ticket` 等设备指纹 Cookie、UA/Referer 异常 | 我们跑在用户脚本里，Cookie 自动带全、UA 是浏览器本体，这块天然占优；保持 `Referer/Origin` 语义正确即可 |
| Greasy Fork「[Bilibili] 关注管理器」反馈区 | 「一次导 50 个没延迟 = 百分百风控」；有用户批量关注约 530 人后被**强制实名认证**，3 天才解除 | 必须在 UI 明确警示账号级后果；单轮设置写操作总量上限 |

### 9.2 可直接借鉴的结论

1. **没有任何项目靠「固定小间隔 + 重试」解决 -352**。所有可用方案都是：随机秒级延迟 + 遇险即停 + 可续跑。
2. **-352 的正确语义是熔断信号**，不是退避重试信号；继续重试只会延长风控时间、加重账号风险。
3. 写操作延迟量级参考：正常档随机 1.5–8s；保守档随机 5–20s；连续失败进入分钟级冷却。
4. 最稳的兜底是走**网页原生交互路径**（原生控件或原生 fetch 上下文），而不是裸拼 API 请求。
5. 极端后果是账号级风控（强制实名、网页功能缺失数分钟到数天），产品层必须有单轮总量上限与醒目警告。

## 11. 备注

- LLM 阶段（调用 DeepSeek / Kimi / MiniMax 等）不会触发 B 站风控；问题只发生在写回 B 站的阶段
